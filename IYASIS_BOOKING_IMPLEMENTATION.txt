システム構成
[GitHub Pages]
reserve.html または新しい booking.html
      ↓ HTTPS fetch
[Cloudflare Worker]
iyasis-booking-api
      ↓ Server-side only
[Square APIs]
- Bookings API
- Catalog API
- Locations API
- Customers API
- Team API（必要に応じて）

重要なセキュリティ要件
- Square Access TokenをHTML、JS、GitHub、コミット履歴へ絶対に保存しない。
- TokenはCloudflare Workers Secretsで保持する。例: SQUARE_ACCESS_TOKEN
- .env / .dev.varsを使用する場合は.gitignoreへ追加。
- CORSは本番では https://toyotsuspa-coder.github.io のみに制限する。
- ユーザー入力を検証する。
- booking APIにはレート制限または簡易bot対策を検討する。
- idempotency_keyを使用し、多重予約登録を防ぐ。

Cloudflare Workerに必要なエンドポイント

1. GET /api/config または GET /api/services
目的:
- フロントに表示する予約可能サービス情報を返す。
- Square Catalog APIの予約対象Service Variationと紐付ける。

返却例:
{
  "services": [
    {
      "key": "trial45",
      "name": "初回ドライヘッドスパ 45分",
      "price": 4000,
      "duration": 45,
      "serviceVariationId": "..."
    }
  ]
}
※秘密情報は返さない。

2. POST /api/availability
request例:
{
  "serviceKey": "trial45",
  "date": "2026-11-21"
}

Worker処理:
- serviceKeyをサーバ側のservice_variation_idへ変換。
- Square POST /v2/bookings/availability/search を呼ぶ。
- location_id、service_variation_id、必要ならteam_member_idを指定。
- Asia/Tokyoの対象日で検索する。
- フロントには必要な startAt / teamMemberId / serviceVariationId 等だけ返す。

response例:
{
  "slots": [
    {"startAt":"2026-11-21T10:00:00+09:00","label":"10:00","teamMemberId":"..."},
    {"startAt":"2026-11-21T11:30:00+09:00","label":"11:30","teamMemberId":"..."}
  ]
}

3. POST /api/bookings
request例:
{
  "serviceKey":"trial45",
  "startAt":"2026-11-21T10:00:00+09:00",
  "teamMemberId":"...",
  "name":"西 息吹",
  "phone":"09012345678",
  "email":"example@example.com"
}

Worker処理:
A. 入力検証
B. 空き枠をSquareでもう一度確認（TOCTOU対策）
C. Customers APIで既存顧客検索または新規顧客作成
D. Square Bookings API create booking
E. idempotency_keyを指定
F. 成功時だけbooking idと表示用情報を返す

response例:
{
  "ok":true,
  "bookingId":"...",
  "startAt":"..."
}

エラー時:
- 409: 直前に枠が埋まった → 「この時間は予約済みになりました。別の時間をお選びください」
- 400: 入力不備
- 500/502: Square側またはWorker側エラー → 「予約を確定できませんでした。時間をおいて再度お試しください」

Square側で確認・取得するID
- LOCATION_ID
- 各コースの service_variation_id
- 必要なスタッフの team_member_id
- Square API version
- Sandbox Access Token（最初）
- Production Access Token（本番移行時）

開発手順
Phase 1: Square Sandbox
1. Square Developer Consoleで IyasisBooking アプリを作成。
2. SandboxでLocation、サービス、スタッフを準備。
3. Cloudflare Workerを作成。
4. SQUARE_ACCESS_TOKENをWorker Secretへ登録。
5. /api/availabilityを実装して、本当にSquareのSandbox空き枠を返す。
6. /api/bookingsを実装してSandbox予約を作成。
7. 癒sis予約画面からWorkerへ接続。
8. 空き枠選択→顧客入力→予約→Squareカレンダー反映を確認。

Phase 2: Production
1. ProductionのLocation ID / service variation IDs / team member IDsを取得。
2. Production tokenをWorker Secretへ安全に設定。
3. CORSをGitHub Pages本番originのみにする。
4. テスト用の実予約を営業時間内の安全な枠で1件だけ作成し、すぐ確認・必要に応じキャンセル。
5. reserve.htmlへの導線を新画面へ切替。
6. Google Business Profileの予約URLも必要に応じ新予約画面へ変更。

GA4計測
既存測定ID: G-FC0KSLFKNN
最低限以下を計測する。
- booking_course_select: コース選択
- booking_date_select: 日付選択
- booking_time_select: 時刻選択
- booking_form_start: 顧客情報画面表示
- booking_submit: 予約ボタン押下
- booking_complete: Square予約成功
- booking_error: 予約失敗

コンバージョン漏れを防ぐため、booking_completeはSquare API成功後のみ発火する。
個人情報（名前、電話、メール）をGA4へ送信しない。

プロトタイプから本番へ変更する箇所
- mockAvailability() を削除。
- 固定TIMESを削除。
- /api/availability の結果で時間ボタンを描画。
- confirmBooking() の待機デモを削除。
- /api/bookingsを呼ぶ。
- APIエラー表示を追加。
- loading stateを空き枠取得にも追加。
- dateOffsetが変わったときselectedDateが古い配列を参照しないよう状態管理を修正。
- dateKey()でtoISOString()を直接利用するとJST日付がUTCずれする場合があるため、Asia/Tokyo基準でYYYY-MM-DDを作る。

実装上の判断
- 最初はスタッフ指名なしで「空いているスタッフなら誰でも」でよい。
- Square Search Availabilityで返ったteamMemberIdをそのまま予約作成に使用する。
- スタッフ指名機能は後から追加する。
- 決済は初期フェーズでは現行運用を維持。予約APIとオンライン決済を同時に作り替えない。
- キャンセル・変更は初版では既存Square導線または電話/LINEへ案内し、予約作成を先に安定させる。

受け入れ条件
- スマホで3タップ程度で日時選択まで進める。
- Squareに存在しない空き枠を表示しない。
- 同じ枠への通常の二重予約を防ぐ。
- 予約成功した場合だけ完了画面を表示。
- Squareカレンダー側に予約が反映される。
- Access TokenがGitHubのソースやDevTools Network responseに露出しない。
- モバイルで入力しやすい。
- 既存index.html、menu.html、access.html等を壊さない。
